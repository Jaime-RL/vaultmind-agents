# Roadmap autónomo de VaultMind (22-29 nov 2026)

Entrega: lunes 30-11-2026 a las 00:59. Este roadmap lo ejecuta un agente de código trabajando solo,
fase a fase. Cada fase es una rama y una PR independiente, para que se pueda revisar, mergear o
descartar por separado. Orden = prioridad: si se acaba el tiempo, lo que falte es lo menos importante.

## Reglas para todas las fases

- **Sin atribución a una IA** en commits, PRs ni código (`Co-authored-by`, «Generated with»…).
  Autor de los commits: `Jaime-RL`.
- **No crear ni editar PRs por la API** (la plataforma añade un pie «Generated by»). Se sube la rama
  y se da el enlace `compare/develop...<rama>?expand=1` para que la persona cree la PR.
- **No hacer push a `develop` ni a `main`.** No hacer merge.
- **Base de cada rama:** `origin/develop` actualizado; si la fase anterior aún no está mergeada,
  partir de su rama y decirlo en la descripción de la PR.
- **`contracts/`** solo cambia en su propia fase (rama `contracts/...`), con `npm run gen:types`
  regenerado. Las PRs de frontend se marcan «para revisión de Iván».
- Tests sin red ni LLM (`FakeLLMClient`, `httpx.MockTransport`, fixtures). Antes de cada push:
  `uv run ruff check . && uv run ruff format --check . && uv run pytest` (backend) y
  `npm run lint && npm test && npm run build && npm run check:types` (frontend).
- Nunca leer ni escribir `.env`. Variables nuevas en `.env.example` (y en `render.yaml` si aplican).
- Al cerrar cada fase: entrada en `docs/ai-log.md` y una línea en el resumen final.

## Fase 0 · Punto de partida
- Rama de trabajo: si `fix/related-gaps` no está en `develop`, partir de ella.
- Comprobar que todo pasa en verde antes de tocar nada.

## Fase 1 · Contrato de la revisión (`contracts/proposal-review`)
- `contracts/proposal.schema.json`: campo opcional `review` en `Proposal`:
  `{claims: int, supported: int, issues: string[], revised: bool}`.
- `backend/app/contracts.py`, `npm run gen:types`, test de deriva contrato ↔ Pydantic.
- **Hecho cuando:** CI verde y tipos regenerados sin diferencias.

## Fase 2 · Revisión guardada en cada nota (`feature/review-in-proposal`, backend)
- `agents/editorial.py`: adjuntar la revisión final a la `Proposal` antes de publicarla
  (`revised=True` si el Redactor corrigió).
- `fixtures/demo_run.json` y `scripts/make_run_fixture.py`: la demo también lleva revisión.
- Tests: la propuesta guardada incluye `review`; la reescrita lleva `revised=True`.

## Fase 3 · Confianza visible (`feature/confidence-badge`, frontend)
- `features/review/ReviewPanel.tsx`: insignia «5/5 respaldadas · 3 papers» (verde = todo,
  ámbar = ≥ 60 %, rojo = menos), etiqueta «Corregida por el Revisor» y lista desplegable de
  problemas. Validar colores con el validador de la skill de dataviz (daltonismo).
- `features/review/NoteMarkdown.tsx`: avisos de Obsidian (`> [!warning]`, `> [!note]`) como avisos.
- Tests con Testing Library para los tres colores, «corregida» y el aviso.

## Fase 4 · SmartRoute en directo (`feature/live-savings`, frontend)
- Contador de coste y ahorro que se actualiza con cada `route_decision` y animación breve al escalar.
- Reutiliza los eventos actuales (sin cambiar contratos). Tests del reductor.

## Fase 5 · Pregunta a tu bóveda (`contracts/ask`, `feature/ask-backend`, `feature/ask-frontend`)
- Contrato `contracts/ask.schema.json`: `AskRequest {question}`, eventos SSE `ask_token`,
  `ask_citation {note_id}`, `ask_done {stats}`.
- Backend: `vault/search.py` (BM25 sin dependencias, por título + contenido), `agents/asker.py`
  (top-k notas → respuesta que cita `[[nota]]`; tarea `answer_question`: SLM primero, escala si no
  cita ninguna nota o la respuesta es vacía), `api/ask.py` con SSE. Respeta el modo público
  (incluye notas aprobadas del visitante) y el cupo diario.
- Frontend: pestaña «Preguntar», respuesta en streaming, citas clicables que resaltan el nodo.
- Tests: BM25, validador de citas, endpoint con `FakeLLMClient`, componente con fixture.

## Fase 6 · Utilidad (`feature/note-actions`)
- «Profundizar»: botón en la nota que lanza una investigación con su título.
- «Editar antes de aprobar»: `ProposalAction` admite `markdown` opcional (contrato en su PR).
- «Exportar»: `GET /api/proposals/export` → .zip con las notas aprobadas del visitante.
- Pantalla de bienvenida con 3 temas de ejemplo; notas pendientes visibles en el grafo al recargar.

## Fase 7 · Calidad de la investigación (`feature/research-sources`)
- `agents/semantic_scholar.py`: segunda herramienta (año, citas, venue), con verificación por id
  igual que arXiv. El Investigador elige; se priorizan los papers más citados.
- Caché de búsquedas en memoria con TTL de 24 h.
- Evals con búsquedas grabadas: fixtures de respuestas de arXiv para 3 temas reales.

## Fase 8 · Cierre
- Script `evals/report.py` que genera la tabla del README a partir de `evals.run` (la persona lo
  ejecuta con la clave de Groq).
- Resumen final: ramas, enlaces de PR en orden de merge, variables nuevas de Render y lo pendiente.
